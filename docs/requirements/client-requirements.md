# クライアント要求事項

## 背景・目的
個人開発者(自分自身)が、PMBOKの考え方(WBSによるタスク分解、優先度・期限による進捗管理)を
反映したタスク管理アプリを必要としている。単一ユーザーでの利用を前提とし、
自身の作業をタスク単位で分解・整理・追跡できる状態を作りたい。

併せて、開発過程そのものをPMBOKプロセス(要求定義・WBS・リスク管理・変更管理・振り返り)に
沿って進めることで、転職活動における実務経験・設計レビュー能力のアピール材料とする。

## スコープ(やること)
- タスクの作成・編集・削除・一覧・詳細閲覧(CRUD)
- タスクの親子階層によるWBS的な分解(親タスク1階層 + 子タスクの2階層構成)
- ステータス管理(未着手 / 進行中 / 完了 の3状態)
- 優先度管理(高 / 中 / 低 の3段階)
- 期限(締切日)の設定
- タスクごとの受け入れ基準(Definition of Done)をテキストで保持
- タスクごとの見積り工数・実績工数(時間単位)の記録([ADR-0002](../adr/0002-evm-progress-and-bug-tracking.md))
- 進捗指標(EVM風メトリクス: PV/EV/AC/CV/SV/CPI/SPI/EAC/ETC/VAC)の算出・確認画面。金額ベースではなく工数(時間)をコストの代理指標とする([ADR-0002](../adr/0002-evm-progress-and-bug-tracking.md))
- バグ管理(登録・編集・削除・一覧。関連タスクへの紐付け)とバグ検知度(累計/未解決件数、解決率、バグ密度)の確認
- AWSへの本番デプロイ(単一環境。動作確認後は速やかに削除し課金を止める)
- インフラ層でのBasic認証によるアクセス制限(アプリ機能としての認証ではなく、公開URLの第三者アクセスを防ぐための簡易措置)

## スコープ外(やらないこと)
- アプリ機能としてのユーザー認証・ユーザー管理(単一ユーザー前提のため不要と判断)
- 複数プロジェクト管理(タスクリストは単一。「プロジェクト」概念は持たない)
- タスク間の依存関係(先行/後続タスク)・クリティカルパス計算
- ガントチャート等のスケジュール可視化(スケジュール管理は`docs/pmbok/schedule.md`側で管理)
- リスク登録簿・変更ログ・振り返りのアプリ機能化(`docs/pmbok/`配下のドキュメントとして管理し、アプリ機能にはしない)
- 調達管理、資源管理(負荷管理) — 単一ユーザー個人開発のため対象外
- 通知・リマインダー機能
- 多言語対応(UIは日本語のみ)

## 非機能要件
- 性能: 単一ユーザー利用のため高性能である必要はない。ただしN+1クエリの回避等、基本的な配慮は行う方針を明文化する
- セキュリティ: 一般的なベストプラクティスを採用する
  - HTTPS化、CSRF対策、XSS対策、SQLインジェクション対策(ORM経由のクエリに統一)
  - 入力バリデーション(フロント/バックエンド双方)
  - 環境変数によるシークレット管理(`.env`はコミット対象外)
  - 本番環境はインフラ層のBasic認証で第三者アクセスを制限する
- 保守拡張性: Vertical Slice構成 + 各スライス内はクリーンアーキテクチャ/ヘキサゴナル的な設計とし、SOLID原則に基づくBefore/After比較を`docs/adr/`に記録する
- テスト: TDDで開発する。ユニットテスト(フロント: Jest等、バックエンド: PHPUnit)およびE2Eテスト(タスクCRUDの主要フローを対象)を自動化し、CIで実行する

## 制約条件
- 開発期間: 1日8時間程度 × 2日が上限(Claudeとの対話時間も含む)
- 予算: 総額5000円ほど。うちClaude課金分を除き、クラウド(AWS等)に使える金額は2000円以下。AWSリソースは使い終わったら速やかに削除する
- 技術制約: フロントエンド React + TypeScript、バックエンド PHP + Laravel、DB MySQL(面接先の技術スタックに合わせた意図的な制約)

## 受け入れ基準(Definition of Done)
- タスクのCRUD(作成・編集・削除・一覧・詳細)がフロントエンドから一通り操作できる
- 親子階層(2階層)・ステータス(3状態)・優先度(3段階)・期限・DoDテキスト・見積り/実績工数がタスク属性として保持・表示される
- 進捗ダッシュボード画面でEVM指標(PV/EV/AC/CV/SV/CPI/SPI/EAC/ETC/VAC)が確認できる
- バグの登録・編集・削除・一覧がフロントエンドから一通り操作でき、バグ検知度(累計/未解決件数、解決率、バグ密度)が確認できる
- ユニットテスト・E2Eテストが自動化され、GitHub Actions上でlint + testが通る(EVM計算式の境界値[AC=0, PV=0等]のユニットテストを含む)
- AWS上に本番デプロイされ、Basic認証経由で動作確認できる
- 主要な設計判断がADRとして`docs/adr/`に記録されている
- SOLID原則に基づくBefore(密結合)→After(疎結合)のリファクタリング比較が、クラス図または資料として残されている
